# ADR: Operator access to the asset connector (`overseer`)

Status: proposed (owner decision 2026-11-19: every machine has an `atelo` and an `overseer` account). Implementation: `configs/asset-connector` (`startup.sh`, `overseer_*` variables), tested in `tests/asset_connector.tftest.hcl`. Extends [asset_connector_adr.md](asset_connector_adr.md).

All identifiers (the operator public key, the source address, hostnames) are Terraform Cloud workspace variables; this document uses placeholders such as `<operator-source-ip>` and `<connector-tailnet-ip>`.

## Context

The connector accepts SSH only through OS Login (the owner's Google identity), with project SSH keys blocked and Tailscale SSH off. Agents that operate the other nodes use a second account, `overseer`, with a dedicated key and passwordless sudo. The connector has no such account, so an agent has no break-glass path that does not depend on a Google session.

## Decision

1. Keep OS Login as the owner's way in. Nothing changes in `enable-oslogin`, `block-project-ssh-keys` or `--ssh=false`.
2. The boot script creates a local account `overseer` when two optional metadata values are present (`overseer-ssh-pubkey`, `overseer-source-ip`, fed by two workspace variables that must be set together):
   - password locked (`passwd -l`), so the key is the only credential;
   - `/etc/sudoers.d/90-overseer-nopasswd` (`NOPASSWD: ALL`, mode 0440, validated with `visudo -cf` before install);
   - `authorized_keys` with the public half of a dedicated ed25519 pair made for this host only (the private half stays on the operator machine);
   - `/etc/ssh/sshd_config.d/overseer-restrict.conf`: `Match User overseer Address <operator-source-ip> LocalAddress <connector-tailnet-ip>` sets `AllowUsers overseer`; `Match User overseer` sets `AllowUsers nobody-matches-this`; both blocks set `AuthenticationMethods publickey`. `AllowUsers` values accumulate across the blocks that match: from the permitted source on the tailnet address both apply and `overseer` is listed; from anywhere else only `nobody-matches-this` applies, which admits no one (verified with `sshd -T -C`, OpenSSH 9.6, 2026-11-19). `AllowUsers` in one block and `DenyUsers` in the other would deny every connection. The connector tailnet address is read at boot from `tailscale ip -4`.
3. Fail closed. The restriction is written, validated and reloaded before the key and the sudoers file exist: `sshd -t`, then `sshd -T -C` for the permitted source (must list `allowusers overseer`) and for a documentation address (must not). Each `sshd -T` result is captured into a variable and grepped afterwards; a `sshd -T | grep -q` pipeline under `pipefail` fails on SIGPIPE whenever `grep` stops reading early (exit 141, seen 2026-11-19). A failing check first revokes the key and sudo, then removes the drop-in and fails the boot script, so no failure leaves a key login without the source restriction. When the metadata disappears, the script revokes the key and sudo and locks the password (the account and its home stay). A metadata error other than 404 fails the script instead of reading as "not requested".
4. The IP restriction is part of the model, not an add-on: `overseer` is root-equivalent, so it is key-only, source-restricted and bound to the tailnet interface address.
5. `atelo` with password plus OTP is not provisioned here. The OTP pattern needs a per-user TOTP secret and a password hash on the host; either would live in Terraform state or instance metadata, which would store the second factor next to the first. The owner's OS Login identity fills the `atelo` role on this host. Revisit with Secret Manager plus a one-time enrolment if a local `atelo` is wanted.

## Alternatives

- Project-wide or instance `ssh-keys` metadata: rejected; it bypasses OS Login and is blocked on purpose.
- OS Login for a second Google identity with sudo (`roles/compute.osAdminLogin`): needs a user or service account and IAM changes; rejected for agents because it ties break-glass to Google sessions.
- Tailscale SSH: disabled by design on this host.

## Consequences

- Risk: `overseer` is root-equivalent. Mitigations: key only, one source address, tailnet interface address only, no public SSH port (the only public rule is UDP 41641), an explicit tailnet grant for the operator machine (tailnet repository). Existing wildcard member grants still reach tcp/22 of the tag, so the sshd `Match` is the enforcing layer, not the tailnet policy.
- `metadata_startup_script` is ForceNew in the google provider: any edit of `startup.sh` would recreate the VM (asset CDN outage, new boot disk, new tailnet node). The instance therefore carries `lifecycle { ignore_changes = [metadata_startup_script] }`; `startup.sh` edits land on the next deliberate replacement (`terraform apply -replace`), and a full plan must show the instance as an in-place metadata update or no-op, never a replacement. Metadata updates are applied live without a restart.
- Delivery to the running VM uses the reviewed `tools/node-operator-access` script (same drop-in, order and checks) over the owner's OS Login session with `--skip-atelo-check`, because the owner's OS Login identity fills the `atelo` role here; the account then persists on the boot disk, and the next boot script (once replaced) keeps it idempotently.
- Known limits (independent review 2026-11-19, non-blocking): a failing `tailscale ip -4` aborts the boot script under `set -e` before `revoke_overseer`, so credentials from an earlier boot stay behind that boot's drop-in (stale but still restrictive, not fail-open); the boot script's denied probe varies only the source address (the tool's real-sshd test also varies the local address); and with `ignore_changes` the running VM keeps its old startup script, so unsetting the workspace variables revokes nothing until the next replacement. On the running VM, revocation is `node-operator-access revert`.
- Rollback: `node-operator-access revert <host> --backup-dir <dir>` with the directory printed at apply (removes the account it created, the key, sudoers and drop-in); and unset the two workspace variables and apply (metadata removed), so a future boot script revokes the key and sudo.

## Verification

- `terraform fmt -check`, `terraform validate`, `terraform test` (key and source together, ed25519 only, tailnet source only, absent by default).
- `sshd -T -C user=overseer,addr=<operator-source-ip>,laddr=<ip>` lists `allowusers overseer` and `authenticationmethods publickey`; other source or local addresses list only the nobody entry (simulated 2026-11-19 with OpenSSH 9.6 and the drop-in included from a main file).
- After apply and boot: login as `overseer` with the dedicated key from the operator machine, `sudo -n true`, and a refused login from another source.

## Part 2: the same model on the Oracle micro nodes (runbook, not applied)

The two Oracle micro nodes (Ubuntu 22.04, `ufw` default deny with `tailscale0` and 41641/udp allowed, key-only sshd) are not in Terraform, so the model is delivered by `tools/node-operator-access`: a uv package whose `render` command prints one idempotent root script and whose `apply` command runs it over `ssh` with a safety session held open and then proves the `overseer` login and `sudo -n true`. Without `--execute` it only prints the plan. The script requires an existing `atelo` account (it never creates or changes it, so `atelo` keeps its current key or password-plus-OTP path and gets no sudo), backs up every file it touches under `/var/backups/node-operator-access-<UTC>`, writes the same sudoers and sshd drop-in as the connector, simulates `sshd -T -C` for the permitted source (allowed), a documentation address (denied) and `atelo` (unaffected), reloads only after those pass, and restores the backup on any failure. Each `sshd -T` result is captured into a variable and then grepped, because a `sshd -T | grep -q` pipeline under `pipefail` fails on SIGPIPE whenever `grep` stops reading early (exit 141 on 2026-11-19). The script prints its backup directory as `NODE_OPERATOR_ACCESS_BACKUP=<dir>`; when the post-apply `overseer` login or `sudo -n true` fails, the CLI runs the revert script for that directory itself, which also deletes the `overseer` account when this run created it (marker `created-user` in the backup) and otherwise restores its previous `authorized_keys`. `apply` takes `--overseer-public-key-file` and `--overseer-private-key-file` (the dedicated pair, checked to match with `ssh-keygen -y`; the private half only proves the new login), `--tailnet-host` (the node's tailnet name, where `LocalAddress` matches) and `--ssh-arg` for the sudo account's connection. The key must be a plain `ssh-ed25519` key with a comment of letters, digits and `@._+-`, and is shell-quoted when rendered. Tests run the rendered scripts in a temporary root against fake `sshd`, `tailscale` and account commands (including `sshd -T` output larger than a pipe buffer), evaluate the drop-in with a real `sshd -T` on Linux, and run in the `Tools` workflow. Not run on the nodes: it waits for Gabriel's go. The existing `ubuntu` account with NOPASSWD sudo stays until `overseer` is verified; its removal is a separate decision.
